# Экспериментальный канал Windows

`ScalarMotion` исполняет пружину LabMotion через Windows Composition. На поток UI
возвращаются события наблюдения; интегрирование и привязки свойств `Visual`
выполняются композитором. JS, локального интегратора и покадрового UI-таймера нет.

`Spring` принимает `ResponseMilliseconds > 0` и `0 <= Bounce < 1`.
Параметризация соответствует `src/motion/model.ts`: `ω = 2π·1000/response`,
`k = ω²`, `c = 2·(1 − bounce)·ω`. Штатный `InteractionTrackerInertiaMotion`
получает ускорение `−k·(x − target) − c·v` и интегрирует его сам.

Положение — в локальных единицах tracker; скорость — в тех же единицах в секунду.
Обычный конструктор сохраняет эти единицы. Для безразмерного прогресса используйте
`ScalarMotion.CreateProgress(compositor, initial)`: его значения находятся в
диапазоне 0…1, скорость измеряется в единицах прогресса в секунду. Внутренний
масштаб скрыт в адаптере. Пересчёт физических пикселей при смене DPI остаётся
отдельной задачей геометрии потребителя.

Координатный конструктор требует явные `initial` и `endpointAccuracy` в единицах
координаты. Потребитель переводит свой допустимый endpoint error в эти единицы:
для смещения это может быть половина физического пикселя, делённая на текущий
`RasterizationScale`; для проекции `q = -y / H` точность `0.001` по q даёт
`endpointAccuracy = 0.001 * H`. Значение должно быть положительным и конечным,
а его квадрат — представимым в единицах исполнителя. `CreateProgress` задаёт
ранее квалифицированную точность `0.001` самостоятельно.

```csharp
using var motion = ScalarMotion.CreateProgress(visual.Compositor);
using var binding = motion.Bind(visual, ScalarProperty.Opacity);
await motion.AnimateTo(1, new Spring(350, 0));
```

`Bind` поддерживает `OffsetX`, `OffsetY` и `Opacity`. Выражение
`position * multiplier + offset` вычисляется композитором в публичных единицах
канала. Геометрия и степень эффекта принадлежат потребителю. `BindOffsetX` —
сокращение для прямой координатной привязки.

У каждой пары Visual/свойство одна активная привязка LabMotion. Повторный `Bind`
заменяет её; освобождение старого handle или канала не останавливает новую.
Другие свойства не затрагиваются. Handle и канал освобождаются на потоке
владельца. Перед прямой записью свойства или запуском чужой Composition-анимации
освободите его привязку LabMotion: произвольную внешнюю замену адаптер не отслеживает.
Для visual из `ElementCompositionPreview.GetElementVisual` это относится и к XAML:
он может записать локальное значение свойства при следующем layout tick и снять
анимацию. В примере Opacity оставлена в XAML по умолчанию, начальную прозрачность
задаёт канал прогресса. См. [правила совместного владения visual](https://github.com/microsoft/WindowsCompositionSamples/wiki/XAML-Composition-Interop-Behavior-Changes).

Один экземпляр принадлежит потоку с `DispatcherQueue`. `AnimateTo` заменяет
предыдущую операцию с результатом `Stopped/replaced`. При retarget из Inertia
текущие позиция и скорость сохраняются. Явная начальная скорость допустима из
покоя, когда нет активной операции. `SnapTo`, `Stop` и `Dispose` различаются
причиной результата; только native Idle активного request в пределах заданной
`endpointAccuracy` завершает его как `Finished/settled`. Это не обещание
математически точного равенства координаты цели. Requests, устаревшие callbacks и bindings
принадлежат адаптеру. Ошибка native admission отклоняет Task.
После окончательного Idle адаптер освобождает request до внешнего уведомления;
поздние callbacks этого request не меняют фазу и не публикуют новое движение.

Native request и даже его `Inertia` не подтверждают применение новой цели:
окончание прежнего возврата в границы может прийти с новым request id.
Адаптер сохраняет цель каждого намерения. При фактическом matching `Idle` вне
её точности он один раз продолжает движение из подтверждённого покоя с нулевой
добавочной скоростью, сохраняя `Operation` и `Origin`. Промежуточный Idle не
публикуется как terminal и не завершает Task. Повторный промах даёт наблюдение
`continuation-failed` и отклоняет ещё ожидающую Task; цикл повторов невозможен.
Новая цель получает собственную попытку, а Stop, Snap, Dispose и новый владелец
отменяют прежнее продолжение. `SetTarget` после окончательного Idle сохраняет
только намерение следующего отпускания.

## Ввод в сырой координате

Координатный конструктор принимает `ScalarAxis.X` или `ScalarAxis.Y`. Ось
одновременно определяет bounds, силу, скорость, наблюдения и привязки.
Для вертикального viewport `Position` совпадает с native Y; обычно визуальное
смещение имеет противоположный знак:

```csharp
using var motion = new ScalarMotion(viewport.Compositor, ScalarAxis.Y, -640, 320,
    initial: 0, endpointAccuracy: 0.001f * 320);
motion.SetTarget(-320, new Spring(350, 0));
using var binding = motion.Bind(content, ScalarProperty.OffsetY, -1);
using var pan = motion.AttachPan(viewport);
// В Touch PointerPressed: pan.Redirect(args.GetCurrentPoint(null));
```

Границы в примере относятся к viewport высотой 320 DIP. Геометрия остаётся
у потребителя. `AttachPan` требует явно заданную цель и пружину; `CreateProgress`
к вводу не подключается, поскольку native drag и release работают в сырых
координатах. Безразмерный progress можно получить проекцией сырой координаты.

`SetTarget` меняет цель и пружину текущей Inertia и следующего отпускания. Его
можно вызывать во время drag: из `Idle` и `Interacting` он не запускает движение.
Во время активной Inertia адаптер повторно выбирает native modifier с нулевой
добавочной скоростью, сохраняя позицию, скорость и логическую принадлежность
движения. Это позволяет сменить цель и во время штатного возврата в границы.
Предыдущий native request больше не может прислать действующий `Idle`.
Ожидание прежней программной анимации заканчивается `Stopped/target-changed`, поэтому оно не подтвердит
достижение уже заменённой цели. `AnimateTo` объединяет установку намерения с
попыткой запуска; `RequestIgnored` отклоняет эту попытку, сохраняя намерение.
Проверка фазы на UI-потоке не делает асинхронные настройки и native Try атомарными.
Продолжение после `SetTarget` наблюдается через `Observed`; его отказ не
переписывает уже окончательный результат `Stopped` прежней Task.

`Observed.Origin` различает `Animation`, `Input`, `Initial`, `Snap` и `Stop`.
Ввод поступает и без ожидающей Task; его `Operation` равен 0 и не завершает чужую
программную операцию. Поля `NativeRequestId`, `NativePosition`,
`NativeReadbackPosition` и `NativeVelocityVector` сохраняют исходные данные WinUI
для диагностики. Управление компонентом не требует этих идентификаторов.

`SnapTo` и `Stop` отправляют команду и прекращают локальное ожидание прежней
анимации. `requested` означает отправку; `value`, `idle` или `ignored` передают
реально полученный callback. Для no-op callback может отсутствовать: общего
обещания native ACK и публичного `Ready` нет. Ненулевой старт Touch-примера
ожидает `Initial/value` с фактической позицией и readback перед приёмом ввода.

Viewport должен оставаться неподвижным. Handle `ScalarPan` принадлежит потоку
канала; его `Dispose` отключает источник и публичные input-наблюдения, но не
обещает остановки уже начатой Inertia. Внутренняя фаза продолжает учитывать
native callbacks. `ScalarMotion.Dispose` освобождает источники и визуальные
привязки, завершает ожидающую Task и подавляет поздние наблюдения.

`Dispose` сначала закрывает канал для повторных вызовов и завершает активную
операцию как `Stopped/disposed`, затем по одной попытке освобождает все собственные
привязки и Composition-ресурсы. Отказ одного cleanup не отменяет последующие;
первая ошибка возвращается с исходным stack trace, подписки `Observed` очищаются
при любом исходе. Внутри привязки ошибка StopAnimation не подменяется ошибкой
освобождения выражения или снятия ownership. Повторный `Dispose` не повторяет
внешние эффекты; ошибку native освобождения это не превращает в успешный release.
Первый вызов по-прежнему требует поток владельца.

## Область опыта

Проверены Windows 11 build 26200, Windows App Runtime 2.6.4, .NET 10.0.403,
WinUI x64 unpackaged и масштаб 1.5. Проверка запускает реальные программные
сценарии в WinUI Window: движение до ±200, retarget после ±40 к ∓100,
сохранение ненулевой скорости против варианта со сбросом, спокойную пружину,
начальную скорость 600, Stop, SnapTo и Dispose. События берут значение из
`InteractionTrackerValuesChangedArgs.Position`; `ReadbackPosition` отдельно
читает `InteractionTracker.Position.X`. Эти сценарии проверяют координату
tracker и завершение операций. Видимое смещение привязанного `Visual` требует
отдельной проверки кадров.

Это не публикуемый пакет (`IsPackable=false`). Жесты sheet, смена DPI/геометрии
и производственные потребительские гарантии ещё требуют реализации и проверки.
Калибровки и стили потребителя в библиотеку не входят.

## Воспроизведение

В репозитории находятся настоящий WinUI-потребитель
[`examples/windows`](../../examples/windows/) и
[`test/windows/verify.ps1`](../../test/windows/verify.ps1). Нужны Windows с
доступным Composition, .NET SDK 10.0.403 и PowerShell. Точная версия SDK и
`rollForward: disable` закреплены в [`global.json`](../../test/windows/global.json).
Из корня репозитория:

```powershell
pwsh -File test/windows/verify.ps1 -OutputDirectory "$env:TEMP/motion-windows-run"
```

Каталог результата должен быть новым. Проверка собирает девять lifecycle-проб
и пятнадцать проверок привязок и единиц прогресса, затем запускает двадцать три
сценариев в настоящем WinUI Window. В lifecycle-пробах
подменена только граница Composition; интегрирование проверяется отдельным
WinUI-потребителем. Сброс скорости служит контролем для retarget, а вызовы
из Idle observer проверяют окончательность результата завершённого движения.
Тот же C# consumer включает одиннадцать cleanup-проб: здоровый Dispose, отказы
binding и каждого собственного ресурса, compound failure, повторный вход и отказ
чужому потоку. На этой границе проверяются попытки освобождения и сохранение первой
ошибки; подмена не доказывает освобождение реального Composition при shutdown.
Двенадцать boundary-сценариев проверяют настоящий выход за обе границы и
возврат в progress и сырых X/Y, здоровую внутреннюю цель, а также `SetTarget`
во время native correction. Для каждого сохраняются 128 наблюдений, прежний
предел 5 секунд и точность `0.001` в координате потребителя q. Смена цели не
переписывает `Stopped` старой Task, а конечный Idle принадлежит последнему request.

Приложение поставляет .NET и Windows App SDK вместе с собой; глобальная установка
App Runtime не требуется. Параметры пружин — данные примера, без зависимости
от другой дизайн-системы. Скрипт проверяет код завершения, полный состав
сценариев и наличие нативных событий. Недоступный runtime, таймаут и отсутствующий
trace завершают проверку ошибкой. Журналы сборки, trace, результаты и хеши
исполняемых файлов сохраняются в каталоге результата.

После запуска скрипт явно проверяет непустой ненулевой handle и тип времени
запуска до чтения остальных identity и ожидания завершения. PowerShell может
вернуть `null` при отказе getter; в таком случае проверка создаёт наблюдаемую
ошибку, затем пытается завершить свой процесс и освободить его через `finally`.

При неуспешном завершении boot-ветка перед прежним throw выводит только проверенные
`completed`/`exitCode`/`traceExists`. Если уже сохранённый trace существует, один раз
читается его JSON и выводится закрытая проекция: `status` (`captured`/`error`/null),
`knownFailureCode` по точной известной первой строке MainPage Require/Until и
`lastRunKind` из конечного состава MainPage. Последний сохранённый run — не текущий
failed run: отказ до `runs.Add` может оставить предыдущий run или null.
Новые `errorType` и `activeProbe` читатель берёт только из закрытых producer полей.
MainPage catch классифицирует фактический `Exception.GetType()` точным сравнением
с известными .NET типами: InvalidOperation/Timeout/ObjectDisposed/Argument/
ArgumentOutOfRange/ArgumentNull/InvalidCast/NullReference/COM. Неизвестный тип,
включая derived type, даёт null. Локальный enum `activeProbe` устанавливается
непосредственно перед существующей awaited пробой IdleRetarget/Retarget/Settle/
Lifetime/Progress; перед записью captured результата очищается. Это активная
верхнеуровневая проба, не stack-site, точный variant, нарушенный assertion или RCA.
Ошибка записи captured результата не приписывается последней успешной пробе.
Save добавляет эти поля к прежним status/error/scale/runs; captured выводит null.
Unknown errorType и known activeProbe независимы; старые trace без новых полей
дают два null, даже если display error содержит полный допустимый stack-frame.
`Exception.ToString()` предназначен людям и не имеет точного формата; multiline
Message может выглядеть как stack. Поэтому новые поля из него никогда не выводятся.
Исторический knownFailureCode остаётся точной текстовой категорией прежней карты,
не удостоверяет actual exception type или active probe. Reader допускает только
case-sensitive enums/string при status=error, не raw error/stack/path/HRESULT.
Пять полей сохраняют прежний cap180символов без новых file reads или ожиданий.
`ConvertFrom-Json -NoEnumerate` сохраняет тип root JSON: массив, включая singleton,
не допускается как MainPage object и выдаёт только nullable поля.
Неизвестные, повреждённые и недоступные значения остаются null; raw error/stack,
массивы runs, путь и identity процесса не выводятся. Эта диагностика не допускает
неуспешный boot и не меняет timeout/cleanup. `process-cleanup.test.ps1` извлекает
исходную AST-функцию и boot-ветку, проверяет JSON controls, healthy silence и
сохранение первичного throw при отказе чтения/вывода.

Без `LAB_MOTION_PROBE_OUTPUT` приложение открывает интерактивный пример нажатия.
Он наблюдает штатный `Button.IsPressed`, поэтому мышь, клавиатура и отмена ввода
остаются в ведении WinUI. Пример использует opacity-привязку, учитывает системное
отключение анимаций и локальный переключатель, снимает подписки при `Unloaded`.
Это технический пример LabMotion, без стилей и токенов внешней дизайн-системы.

Полную проверку ввода запускают после сборки consumer в одноразовой
GitHub-hosted Windows-сессии с PowerShell 7 и Node:

```powershell
pwsh -File test/windows/verify-input.ps1 -ApplicationDirectory "$env:TEMP/motion-windows-run/app" -OutputDirectory "$env:TEMP/motion-input-run" -ConfigureHostedAnimations
```

Проверка ввода принимает `HasExited` только как `bool`, а `ExitCode` — как `int`.
После очистки она повторно читает завершение и записывает `close.json` из уже
проверенных значений. При `null` или неверном типе очистка пытается завершить
собственный процесс и сохраняет ошибку чтения, даже если ввод уже не прошёл.
`finally` освобождает процессы и восстанавливает окружение и настройку.
Первая ошибка очистки сохраняется до конца, а следующие сообщаются предупреждениями.
Ошибка ввода остаётся основной; без неё любая ошибка очистки завершает проверку
отказом. Восстановление каждой переменной окружения выполняется независимо.
Если Close/Wait не завершились штатно, очистка перед Dispose отдельно пытается
вызвать Kill/Wait один раз. Ошибка forced stop наблюдаема; повторного Kill нет.
`cleanup.test.ps1` проверяет эти пути на подменных процессах и отдельно проверяет
отказ getter у настоящего неассоциированного .NET Process без запуска процесса.
`Finish-Tool` отдельно сохраняет первую ошибку ожидания winapp и перед Dispose
пытается вызвать Kill ровно один раз, даже если Wait выбросил исключение.
Оба ожидания расходуют один исходный Timeout, отсчитываемый монотонно с входа;
после его исчерпания Kill всё равно вызывается, а повторное ожидание получает 0.
Неподтверждённое завершение и вторичные отказы остановки или Dispose наблюдаемы,
но не заменяют первую ошибку. После штатного завершения Kill не вызывается,
в том числе при последующем отказе чтения stdout или записи evidence.
Эти пути проверяются отдельными подменами настоящего Finish-Tool из AST.

Скрипт скачивает официальный winapp CLI 0.7.1 с проверкой SHA256, запускает своё
окно и передаёт ему мышь и Space через системный ввод. Он требует события
WinUI, промежуточные значения движения и возврат в покой. Девять сценариев включают
отдельные локальное и системное отключения во время движения, ввод down/up при
каждом запрете и новое animated-движение после системного включения. При системном
запрете локальный переключатель остаётся включённым. Oracle требует `Stopped/snap`
старой операции, snap-readback и отсутствие позднего движения после системного запрета.
Animated-сценарии требуют обе включённые настройки.
Для `disable-animation` и `system-disable-animation` скрипт запускает прежнюю release-команду через
`Start-Tool`, затем до ожидания выхода CLI наблюдает release intent и незавершённый
request приложения. Локальный сценарий использует свой исходный drag из BeforeArguments
как release child, затем отправляет прежний Space в Animation через Invoke-Ui;
результат Space и результат release проверяются отдельно. Системный `Write(false)`
либо запуск локальной Space-команды следуют сразу после этой выборки;
задержанный CLI exit больше не обязан предшествовать наблюдению. Его результат всё
равно проверяет `Finish-Tool` в `finally` на том же child, в том числе после ошибки
чтения trace, локальной команды или системного setter. Первая ошибка сохраняется, вторичная ошибка
завершения сообщается предупреждением. Наблюдение ограничено прежними 8s и расходует
исходные 30s tool cap: `Finish-Tool` получает только остаток, без нового полного срока.
Остальные семь сценариев сохраняют синхронный `Invoke-Ui`.
`value` кадра буферизуется, поэтому скрипт не ждёт его записи в файл перед setter.
Прежняя итоговая проверка требует промежуточное движение до `systemPreference`, остановку
через `Stopped/snap` и snap-readback. Если операция успела settled между выборкой
и фактическим запретом, опыт отклоняется; split не гарантирует попадания в активное окно.
Синхронное ожидание release CLI больше не предшествует локальной Space-команде,
но её доставка сама может опоздать: strict interruption/snap oracle не ослаблен.
Настройка, flags2, восстановление и producer Flush не меняются. Подменные controls
исполняют настоящие `Scenario`, `Invoke-Ui` и `Finish-Tool` из AST, но не доказывают
доставку системного callback или причину отказа после уже выполненного `Write(false)`.
Отдельные local controls используют настоящий Scenario с исходными BeforeArguments:
healthy/delayed CLI, уже settled и race, ошибки чтения/Space/exit и независимый
release Finish. Это подготовленные подменные controls, не native RCA системного отказа.
Если shared guard не увидел `completed/snap`, первичная ошибка называет локальный
или системный сценарий. В той же `failure.txt` она сохраняет последнюю уже
прочитанную выборку: до 12 строк фаз после начала сценария, без нового чтения trace.
`input-phase` schema2 содержит `after`, `count`, `omitted`, `invalid` и `rows`;
поля строки — sequence, phase, operation, nativeOperation, pressed, localAnimation,
systemAnimation, reason, end, isCurrent, notification, queued, diagnosticFailed;
поле с индексом 13 — nullable снимок подписки из `completed`.
Фазы `systemCallback`, `systemQueued`, `systemDelegate` отдельно показывают допущенный
адаптером `UISettings.AnimationsEnabledChanged` callback, возвращённый `TryEnqueue`
bool и начало managed делегата. В trace источник явно указан как
`UISettings.AnimationsEnabledChanged`; это не receipt `WM_SETTINGCHANGE` или
подтверждение применения настройки. Первые 13 полей прежней проекции не изменены.
Снимок подписки — массив Registration, RawEntries, AdmittedEntries, LastEntry,
LastEntryQpc, QpcFrequency, Attached, Active, Faulted, subscriptionIsCurrent.
`LastEntry` имеет только значения None/Admitted/Rejected. `RawEntries` считает входы
до проверки допуска под существующим lock адаптера, `AdmittedEntries` — прошедшие
её входы, не успешные enqueue или эффекты. Отклонённый поздний callback поэтому
не требует записи Received. QPC берётся на входе callback; порядок получения lock
при конкурентных вызовах может отличаться от порядка QPC.
Счётчики накопительные за жизнь экземпляра, не за отдельную операцию.
Registration идентифицирует экземпляр адаптера в процессе, не SPI-запрос.
Экземпляр захватывается до await текущей операции; снимок читает именно его,
даже если позднее подписка страницы заменена. `subscriptionIsCurrent` отдельно
сравнивает его с текущей подпиской; это не operation `isCurrent` и не атомарная
связь с getter или last-issued notification. Состояние и счётчики самого адаптера
снимаются совместно под lock. Attached означает сохранённую подписку, Active —
её допуск, Faulted — сохранённую ошибку, а не подтверждение native снятия.
Счётчики включены только с trace; переполнение безопасного JSON integer даёт null,
не wraparound. Нет снимка/не удалось чтение — null; отсутствие входа в этом
экземпляре к моменту выборки не доказывает отсутствие событий глобально или позже.
Снимок использует существующий completed/Flush, без новых событий, ожиданий,
таймеров, getter, изменения policy или условий приёмки. Его lock/QPC также
имеют observer effect; исчезновение отказа не доказывает причину.
Для различения timing исхода добавлены отдельные `setter` и `timing`, не новые
условия приёмки. `setter` — снимок именно запрещающего вызова: абсолютные QPC
на входе native SET и после его возврата, `SetSucceeded`, QPC после уже существующего
проверочного GET, его bool и частота QPC. Возврат SET и проверенный GET — разные
границы. Этот снимок снимается сразу после `Write(false)` в существующий
`animation-system-disabled.json`; восстановление не заменяет его в failure summary.
`timing` содержит строки sequence, phase, qpc, qpcFrequency, notification,
clientAreaAnimation, outcome, enabled, observed. Поле `clientAreaAnimation` сохранено
для совместимости проекции, но в текущем property-event транспорте всегда null:
у события нет WM wParam, и такой классификатор к нему неприменим. Исторические
WM-записи с этим полем не переименовываются и не превращаются в property receipts.
`systemApply` сообщает Missing/Stale/Detached admission либо Deduplicated/Update
с уже прочитанными bool текущего UISettings и прошлого наблюдения. Дополнительного
getter нет; Update обозначает выбранный вызов, не успешное завершение эффекта.
Запись и её редкий Flush идут после решения dedup/admission или вызова Update.
Так поздний dedup не зависит от будущего completed/Update для записи на диск.
Ошибка диагностики только выставляет прежний sticky flag, не меняет policy outcome.
В completed QPC относится к записи после await, а systemAnimation остаётся отдельным
поздним getter: ни одно поле не устанавливает время effective preference change
или точный native idle. Новых timestamps/Flush в callback кадра нет.

Сравнение допускается только в том же системном/VM запуске с доступными положительными
QPC и совпадающей частотой. Это `Stopwatch.GetTimestamp()`, а не относительные epochs
двух stopwatch. [Контракт Microsoft](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)
указывает фиксированную частоту в пределах boot и неопределённый порядок
межпоточных выборок с разницей не более одного tick. Missing/null, разные частоты
или такое соседство не подтверждают порядок; никаких выводов по ним harness не делает.
Дополнительные sparse timestamps, запись outcome и Flush имеют observer effect:
могут сдвинуть расписание. Исчезновение отказа после instrumentation не является RCA.
`timingCount/timingOmitted` отдельно учитывают обрезку новых строк в том же общем
лимите 1800 ASCII-символов; null означает недоступное/неверное поле. Отсутствие
receipt при пропуске строк или sticky failure не доказывает отсутствие callback.
`notification` связывает три фазы одного callback; в `completed` тот же счётчик
читается как last-issued snapshot, не как receipt для конкретного SPI. Snapshot
счётчика и sticky flag не атомарны. Последующий `systemPreference`
intent по-прежнему содержит прочитанный приложением systemAnimation. Порядок
делегата и записи queue-result может различаться; соседство с intent не является
атомарной связью callback→intent. Сохраняются только фиксированные
перечисления, bool и неотрицательные целые; отсутствующее или неверное поле даёт
null. JSON ограничен 1800 ASCII-символами, пропуски отмечены явно. При `omitted>0`
отсутствие фазы в summary не доказывает её отсутствия в trace. Это диагностика
порядка release/preference/request/completion/snap, без изменения oracle или
сроков. Отказ проекции не заменяет первичную ошибку. Полные trace, CLI arguments,
stdout и пользовательское содержимое в summary не попадают.
Временный native diagnostic receiver включается только с тем же trace и после
успешной исходной typed подписки. Он получает тот же retained `UISettings` через
публичный CsWinRT interop и QI(IUISettings6), без новой активации. Native WRL receiver
с FtmBase записывает лишь bounded count/QPC; policy, managed callback, очередь и
oracle не используют его как источник. Helper DLL собирается установленным VC x64
toolchain внутри прежнего `verify.ps1`, без установки ПО. Синтетический вызов того же
typed ABI до add проверяет recorder отдельно; control count/QPC сохраняются отдельно,
actual counters сбрасываются до checked add. Synthetic PASS не подтверждает OS delivery.

`native` в failure summary — одна последняя completed-выборка захваченной подписки:
sequence, registration, State, SameSource, ControlPassed, SourceHResult,
DelegateHResult, MarshalHResult, ControlHResult, ControlCount, ControlQpc,
QpcFrequency, AddHResult, Count, LastEntryQpc, Attached, Active, Faulted, RemoveHResult.
Это добавочное поле schema 2; прежние row columns, общий предел 1800 ASCII и условия
приёмки сохранены. Нулевой token не считается ошибкой; сам token и адреса не выводятся.
Unavailable/Faulted не трактуется как здоровый source count0. Поздний null completed
сбрасывает старую положительную выборку. Refcounted record удерживается callback,
без ссылки на managed owner или source. Close отзывает active до одной попытки remove;
failed remove сохраняет Attached/Faulted и отдельную cleanup-ошибку, не detached PASS.
Исходный product primary остаётся первым при aggregate cleanup failures. DLL не
выгружается, пока callbacks ещё возможны; safe release не вызывает remove из finalizer.

Только actual entry QPC внутри прежнего SET→completion окна при одинаковой boot/frequency
сужает область к доставке между подписками. Cumulative count не идентифицирует SPI;
поздний entry не доказывает своевременное прерывание. Дополнительный native token/reference
может влиять на fan-out/lifetime; даже исчезновение отказа не доказывает causal fix или
готовность обычного пути без диагностики. После выбора repair этот временный
различитель удаляется либо обычный путь отдельно проверяется без него в прежней приёмке.
Ни control, ни native positive не заменяют original typed input witness.

В режиме trace callback делает один Flush после enqueue: иначе отказ очереди не
имел бы будущего Update, способного записать receipt и false. Этот дополнительный
lock/IO может изменить расписание и не доказывает причину исчезнувшего отказа.
Диагностика не читает XAML из native callback; её catch изолирует только Add/Flush,
а ошибки enqueue отдельно сохраняет adapter. Ошибка Add/Flush сохраняется в sticky `diagnosticFailed` для
следующей доступной диагностической записи; false означает лишь отсутствие ранее
замеченной ошибки. Если следующих записей или рабочего транспорта нет, результат
диагностики неизвестен. Эти события не дают input GREEN и не являются новым gate.
Без trace callback также доставляет уведомление через managed очередь. Отказ
enqueue наблюдаем как ошибка, а не заменяется прямым Update. Единственный источник
системной смены — штатное
[`UISettings.AnimationsEnabledChanged`](https://learn.microsoft.com/en-us/uwp/api/windows.ui.viewmanagement.uisettings.animationsenabledchanged?view=winrt-26100)
того же экземпляра `UISettings`; WM fallback, polling и второго источника нет.
Контракт доступен с Windows 10 2004/19041 (UniversalApiContract v10), что покрывает
минимальную версию примера. Документация не обещает UI-поток callback: его диагностика
использует защищённый lock `PressTrace`, а getter, policy и сообщение в XAML `State`
выполняются только на UI-потоке. В args не предполагается недокументированного bool payload.
На UI-потоке делегат перечитывает тот же `UISettings`; повторные уведомления при
неизменном значении не запускают новые команды движения. Начальное чтение и все
предметные реакции обновляют последний принятый snapshot в одном владельце.
Снятие подписки при Unloaded/Closed не отменяет уже queued delegates;
они не применяют preference к странице и не выдают команды движения, хотя
диагностическая запись начала Delegate может сохраниться.
Каждый обработчик передаёт идентичность своей подписки, а не позднее значение текущей:
старый обработчик после Detach/Attach не выдаёт эффект новой странице.
Отзыв допуска и доставка синхронизированы; перед снятием подписки закрывается допуск к эффекту.
`IsAttached` остаётся true при отказе снятия, чтобы владелец не забыл возможный
сохраняющийся транспорт и не разрешил новый Attach. `IsActive` отдельно закрывает
доставку и Apply; сохранённая ошибка читается до getter. Dispose делает только одну
попытку снятия. В [CsWinRT EventSource](https://github.com/microsoft/CsWinRT/blob/ff5227a4ffca06dfa6de8ca0a5c127c04f294291/src/WinRT.Runtime/Interop/EventSource%7BTDelegate%7D.cs#L214-L237)
managed delegate удаляется до проверки native RemoveHandler: после native отказа
повторный `-=` может успешно ничего не сделать. Поэтому повторный Dispose не
повторяет remove и не превращает неизвестный физический исход в detached;
сохраняются `IsAttached=true`, retired и первый fault. Новый Attach запрещён этим
владельцем. После подтверждённого первого снятия повторного remove также нет.
Ошибки доставки/снятия и сообщения об ошибке сохраняются под общим lock;
сообщение маршрутизируется в UI-очередь и проверяет идентичность подписки.
Регистрация и снятие выполняются на UI-потоке; native HWND/subclass, ручного GC root
и reverse-PInvoke в этом транспорте нет. Ошибка регистрации остаётся видимой вызывающему.
Флаг `-ConfigureHostedAnimations` доступен только в одноразовой GitHub-hosted
сессии: он включает и временно отключает client-area animation через `SystemParametersInfo`,
проверяет системный readback и реакцию приложения через native property event с чтением
того же `UISettings`, затем восстанавливает прежнее значение
при завершении, в том числе после ошибки. Ошибка очистки не подменяет первичную ошибку
ввода или настройки и выдаёт фиксированное предупреждение; `Dispose` приложения и
восстановление окружения/предпочтения выполняются через `finally`.
Без флага полный тест завершается явной ошибкой
до изменения системной настройки. Профиль пользователя
на диск не записывается; приложение продолжает учитывать `UISettings`.
Кадры WGC и снимки окна сохраняются в локальном каталоге результата для
визуального review. Обычный CI не загружает диагностические архивы в GitHub;
его временный каталог не является долговременным хранилищем кадров.
Автоматический результат описывает ввод и движение; качество изображения
проверяется отдельно по кадрам с известной версией приложения.

Для этого запуска `LAB_MOTION_PRESS_TRACE` включает ограниченную JSONL-трассу
в примере. Обычный запуск не регистрирует диагностические наблюдатели и не пишет
на диск. CLI используется только тестом и не входит в библиотеку.
Официальная [документация Microsoft](https://learn.microsoft.com/en-us/windows/apps/develop/ai-assisted/testing)
описывает этот путь для GitHub Windows runner. Сам факт запуска на runner
не подтверждает touch, потерю capture, смену DPI или удержание Space:
этим сценариям нужны отдельные наблюдения.

## Точность прогресса

В предварительном опыте сырая координата 0…1 получала native Idle до достижения
цели с требуемой точностью. `CreateProgress` использует внутренний размах 1000,
сохраняя позицию и скорость в публичных единицах. Это смена единиц существующей
пружины, без второго интегратора и без принудительного скачка в конце анимации.

Нативные проверки задают допуск 0.001 для переходов 0→1, 1→0 и разворота на ходу;
также проверяют промежуточные значения, сохранение скорости и явную начальную
скорость. Допуск относится к этим сценариям и указанной среде. Он не является
доказательством для всех параметров пружины и версий Windows; число 1000
не объявляется оптимальным.

## Завершение у границы

`Inertia` допускает выход за `MinPosition` / `MaxPosition`, а `Idle` требует
возврата внутрь. При безусловном выборе custom force нативный интегратор может
остановиться на малом остатке снаружи и повторно выбирать ту же пружину вместо
штатного возврата в границы. Границы и формула силы поэтому остаются прежними,
а выбор модификатора уступает штатной коррекции только при трёх условиях:
позиция снаружи, цель совпадает именно с этой границей, остаточная энергия
пружины укладывается в заданную точность координаты.

Для `d = x - target`, `k > 0`, `c > 0` величина `A² = d² + v²/k` имеет
производную `-2c·v²/k <= 0`. Следовательно, `A` ограничивает остаточное отклонение
идеальной затухающей пружины с неизменной целью. Условие `A² <= accuracy²`
проверяется самим композитором при выборе Inertia modifier. Оно сохраняет
заданную пружину при раннем развороте, ненулевой значительной скорости и новой
внутренней либо противоположной цели. Точность переводится вместе с позицией
и скоростью; у адаптера нет скрытого допуска в DIP.

Это обоснование момента передачи управления, а не отдельный интегратор или
доказательство траектории штатной коррекции. Нативные проверки требуют реального
`Idle` нужного request, конечной позиции в исходном диапазоне и заданного
endpoint error. Адаптер не подменяет `Finished`, не расширяет bounds и не ждёт
покоя по таймеру.

## Почему используется force expression

`SpringScalarNaturalMotionAnimation` с natural modifier в проверенном runtime
сбрасывала позицию и скорость при программном повторном входе в Inertia.
Это воспроизведено также с новым spring object и начальным выражением из tracker.
Её `Period` дополнительно оказался в 2π раз медленнее параметра LabMotion
`response` при одинаковом численном значении. Эти отрицательные результаты
не переносятся на другие версии ОС без повторной проверки.

[Официальный контракт InteractionTrackerInertiaMotion](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.composition.interactions.interactiontrackerinertiamotion)
прямо задаёт вторую производную позиции и содержит пример силы пружины;
[TryUpdatePositionWithAdditionalVelocity](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.composition.interactions.interactiontracker.tryupdatepositionwithadditionalvelocity)
добавляет скорость в Inertia. Адаптер передаёт ноль при retarget и сохраняет
состояние системного исполнителя.
