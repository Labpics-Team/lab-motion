# Полезная композиция без расширения полномочий

**Diátaxis:** how-to.

Задача процедуры: при локальной работе замечать соседние потребности, сохранять
дешёвую совместимость и замыкать полезные сценарии, не заставляя владельца вручную
перечислять все пары продуктов. Это не бизнес-стратегия, новый планировщик,
универсальный каталог или разрешение интегрировать всё со всем.

Применяй при изменении публичного API, общего типа, схемы, упаковки, контракта
эксплуатации, полномочий либо значимого поведения на границе. Также при подготовке
нового потребителя. Не повторяй проход для каждой строки или неизменной сессии.

## 1. Сначала восстанови потребность, не название репозитория

Из пользовательского намерения и authoritative plan установи, кому нужен результат,
какое действие должно стать возможным и что нельзя потерять. Реализованная сегодня
поверхность не подменяет цель продукта. Явно принятая будущая вариативность является
основанием проектирования; агентская догадка о будущем спросе таким основанием не
является. Не превращай исходный артефакт в потолок амбиции.

Например, SVG может быть авторским исходником вариативной иконографики. Из наличия
SVG нельзя вывести готовность параметрических осей, оптики, смысловых жестов или
генерации агентом. Но нельзя и удалить эти заявленные цели под предлогом, что
нынешний пакет экспортирует только строки. Геометрическая корректность, визуальная
узнаваемость, соответствие стилю и время получения результата требуют разных
доказательств. Допустимая геометрия не означает автоматически красивую иконку.

Рабочая модель имеет пять частей, которые не требуют пяти новых файлов:

| Часть | Источник истины | Вопрос |
|---|---|---|
| Потребность | намерение, принятый сценарий или наблюдаемый consumer | Зачем нужен переход и кто примет результат? |
| Требуемый порт | контракт потребителя | Какие значения, смысл, ошибки, полномочия и бюджеты нужны? |
| Возможность | контракт и реализация производителя | Что действительно предоставляется и в какой области? |
| Связка | владелец интеграции и его evidence | Совместимы ли конкретные версии в выбранной среде? |
| Полный сценарий | consumer acceptance | Дошёл ли полезный результат через все границы? |

Потребитель владеет своим требованием, производитель своим обещанием. Адаптер может
честно переводить разные представления. Общая wire schema не обязана становиться
общей доменной моделью. Имена продуктов и общий транспорт сами по себе не связывают
эти части.

## 2. Расширь внимание на доказанную окрестность

В canonical checkout `agents-config`, после обычной сверки remote:

```sh
node plans/tools/plan-context.mjs --track <текущий-track> --node <NODE-ID>
```

Либо выбери область по каноническому repository и относительным путям. Для поиска
ещё не связанного потребителя используй слова из его необходимого контракта, а не
лозунг «интеграция с нашим продуктом»:

```sh
node plans/tools/plan-context.mjs --repository <owner/repository> --path <путь>
node plans/tools/plan-context.mjs --track <track> --term '<термин контракта>' --depth 2
```

Обзор читает только выбранные ACTIVE-ревизии из одного Git-снимка и находит входящие
и исходящие ссылки. Он различает объявленный blocker, ссылку на узел, упоминание
имени и буквальное совпадение термина. Отрицательное «не зависит от X» остаётся
упоминанием, а не зависимостью. `declaredStatus` является строкой плана, не проверкой
допуска или готовности. Полный контракт CLI находится в `plans/tools/plan-context.md`
того же checkout.

Это навигационный слой, а не полный semantic resolver. Совпадение MCP/OpenAPI/OIDC
не доказывает перенос смысла, прав или состояния. Источник `local-reference-only`
не удостоверяет свежесть remote; она устанавливается обычным preflight. Отсутствие
результата, недоступный источник, пропущенное поле и неполное покрытие не означают
отсутствия потребителей. Исторические Delta/Facts/CAPA/Unknowns не используются для
автоматических рёбер: при нужде открой их как отдельные свидетельства с областью
применимости. Увиденный путь не является чтением его полного содержимого.

После обзора открой релевантные первичные источники: потребительский порт,
экспортируемую схему, адаптер, точку сборки, package exports либо разрешённый runtime
readback. Проверь также уже используемые сторонние решения. Для ещё не связанного
порта ищи по предметным терминам и типам среди доступных contracts/code, а не только
по готовым межплановым ссылкам. Не просматривай всю организацию без различающего
вопроса. Независимая работа продолжается, когда отсутствующий обзор не меняет её
корректность; конкретную неизвестную совместимость не выдавай за проверенную.

## 3. Проверь стык раньше решения «соединить»

Для кандидата установи применимость всех необходимых измерений:

- смысл входов, результатов, ошибок, неопределённости и версии;
- субъект, tenant/resource/action, актуальные права и окончательный владелец эффекта;
- состояние, повтор, отмена, потеря ответа, восстановление и совместимость выпуска;
- полный бюджет пути, эксплуатация, пользовательский результат и цена отключения.

Это независимые вопросы, не лестница `compatible → deployed → used`. Конфигурация
может существовать без рабочего вызова; вызов может работать с неприемлемыми правами;
схема может совпадать при утрате partial result. Неприменимость измерения обосновывается
свойством, а не пустой ячейкой. Доказательства конкретной межпродуктовой связки остаются
по контракту `plans/CAPABILITY-EVIDENCE.md`, а не в новом editable graph.

Попарные проверки не доказывают общий сценарий. Например, общий deadline может
умножиться на нескольких retries, отзыв потеряться на одном hop, а частичный поиск
превратиться в полный ответ после промежуточной обрезки. Проверь реальный путь и
общие инварианты, включая законный успешный исход; система, которая запрещает всё,
не выполнила пользовательскую задачу.

## 4. Сравни добавленную пользу и полную цену

Сравни с вариантом **ничего не связывать** и наиболее простым существующим способом
получить тот же результат. Сначала исключи нарушение hard constraints; затем сравни
полезность в принятом сценарии и дополнительные расходы: реализацию, тестирование,
миграцию, поддержку, когнитивную нагрузку, задержку, ресурсы, полномочия, связанность
выпусков и будущий выход. Уже потраченные усилия и число рёбер не являются будущей
экономией. «Осталась одна настройка» не доказывает, что не нужны ещё semantics,
delegation, recovery и пользовательская приёмка.

Не требуй буквально нулевой цены или идеального Парето-доминирования: это исключит
полезную интеграцию, у которой есть небольшая обоснованная стоимость. Но неизвестное
не приравнивай к нулю. При двух одинаково пригодных вариантах предпочти сохраняющий
заявленную вариативность без лишнего обязательства. Не вводи новые опции «на всякий
случай» и не превращай дополнительные consumers в числовой бизнес-рейтинг.

Если вывод меняется из-за неизвестного, проведи минимальную разрешённую проверку
стыка с заранее названным результатом, меняющим решение. Если полезность уже ясна
по реальному повторяющемуся ручному действию, не требуй исследования рынка ради
удаления этого действия. Если речь о новом рынке, позиционировании, цене или крупной
продуктовой ставке, инженерное совпадение контрактов не выбирает это за владельца.
Механизм и техническая характеристика не становятся рекламным обещанием.

## 5. Выбери действие в действующей области

**Сохранить совместимость сейчас.** Изменение решает текущую задачу, устраняет
конкретную лишнюю прослойку либо сохраняет принятую вариативность; его полная цена
соразмерна, затронутые свойства и потребители проверены. Выполни в текущем срезе,
если действующая авторизация и контракт это покрывают.

**Замкнуть принятый сценарий.** Существует потребительское требование и доказанный
недостающий переход. Через существующих владельцев подготовь минимальную связку,
испытай её и доставь по обычным gates. Не жди полного roadmap соседа, если нужен
только конкретный совместимый output. Не дублируй его state, ACL, scheduler или
runtime ради удобства интеграции.

**Сначала различить.** Есть основание проверить возможность, но неизвестное меняет
выбор. Разрешённый изолированный probe является следующим действием, не доказанной
интеграцией. Не включай внешние записи, новые расходы и полномочия из факта полезности.

**Не связывать или передать отдельно.** Нет принятой потребности, цена непропорциональна,
нарушены границы или это другой фронт. У существенной диспозиции сохрани причину,
владельца и условие пересмотра в существующем PR/плане. Не плодить issues на каждое
упоминание. Найденная возможность не отменяет правила приоритета AGENTS.md.

## 6. Замкни знание после доставки

После merge/readback обнови только затронутые canonical contracts и binding evidence;
через текущий SPEC пересмотри зависимые узлы. Уведоми владельцев применимым mailbox/PR,
сохрани источник и invalidator, а не второй пересказ статусов. Пересчитай обзор при
новом снимке, возвращении после compaction или изменении существенного предположения.
Новый сосед становится поводом проверить возможность, не автоматически `ready`.
Несвязанное изменение main не отменяет стабильное предметное доказательство.

Рабочий результат прохода помещается в существующий evidence/PR: потребность,
конкретный стык, основания, сравнение с отсутствием связи, выбранное действие,
проверка и условие пересмотра. Для очевидного неизменённого стыка отдельный документ
не требуется. Техническая доставка инструкции не доказывает, что модель заметила
связь или стала лучше выбирать; парная оценка находится в
`authoring/composition-evaluation.md` canonical checkout.

## Два различных примера одной процедуры

**Phantom.** Потребность: получать подходящий веб-контент и честный результат поиска
за приемлемую полную цену. Проверяется настоящий Firecrawl Engine contract, а не
слово Firecrawl в README. Meta MCP может быть соседним потребителем через стандартный
адаптер, но Phantom не обязан импортировать его или стать владельцем исследовательской
политики. Tool Loop требует разрешённого tool effect; ID задаёт применимую личность/
делегирование, backend сохраняет финальное решение. Доступность всех компонентов не
доказывает безопасного Plane→GitLab journey; одной записи в roster может не хватить.

**Иконографика.** Потребность: настраивать авторский сет для клиента и получать новый
знак в его характере. Производитель геометрии, оптическая оценка, агентный authoring,
формат экспорта и временное исполнение различаются. Совместимость с Motion возникает
на контракте прогресса/частей/прерывания, не требует scheduler внутри геометрии.
Статический consumer не ждёт morph; valid SVG не доказывает параметрическую семью,
узнаваемость или гарантированный one-shot за секунду. Новый принятый архетип может
расширить пространство будущих знаков без отдельной интеграции каждого знака с UI.
