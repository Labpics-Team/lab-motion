# Передача touch и скорости отпускания

Опыт проверяет непрерывность вертикального жеста и отпускания через штатный
InteractionTracker. Публичный API LabMotion и компоненты LabUI не меняются.
Текущий протокол использует родную координату Y; прежний опыт преобразования
координат сохранён в истории и разобран ниже.

Неподвижный viewport — 480 × 320 DIP с фактической высотой H. Tracker работает
в диапазоне [−H, 0], начальная позиция −H/2. Delta modifiers отсутствуют.
Положение и скорость остаются в одной системе координат при переходе от жеста
к инерции. Прогресс q = −Y/H и скорость q̇ = −Vy/H вычисляются при наблюдении;
видимое смещение задаётся выражением −tracker.Position.Y.
Y source использует EnabledWithInertia. Сила пружины сохраняет response 350 ms,
bounce 0 и цель −H для движения вниз либо 0 для движения вверх.

Два независимых запуска: `y-down`, `y-up`. Swipe начинается на 40 DIP выше/ниже
центра и заканчивается симметрично с другой стороны: 80 DIP за номинальные
300 ms. CLI получает физические экранные координаты после сверки UIA-геометрии
и масштаба. DPI и геометрия не меняются внутри запуска.
В [winapp CLI 0.7.1](https://github.com/microsoft/winappCli/blob/e3cd0b94f3e7b776ac51ba0564f4908094e979b5/src/winapp-CLI/WinApp.UIAutomation/Input/PointerInput.cs#L287)
20 кадров распределяются по заданной длительности с поправкой на прошедшее
время; дополнительной паузы перед отпусканием нет. Это расписание инъектора,
а не измерение фактической скорости ОС.

Каждый каталог содержит `trace.jsonl` приложения, `scenario.json` harness,
identity процесса/исходников, исходные ответы CLI и результат закрытия окна.
Схема сценария 2 отделяет родные координаты от прежней схемы 1:

```json
{
  "schema": 2,
  "coordinates": "native",
  "name": "y-down",
  "axis": "y",
  "direction": 1,
  "gesture": "swipe",
  "durationMs": 300,
  "coordinateSpace": "viewport-dip",
  "start": {"x": 240, "y": 120},
  "end": {"x": 240, "y": 200},
  "viewport": {"width": 480, "height": 320, "scale": 1},
  "injection": {
    "coordinateSpace": "screen-pixel",
    "start": {"x": 400, "y": 300},
    "end": {"x": 400, "y": 380},
    "exitCode": 0
  }
}
```

Экранные координаты примера условны; harness записывает фактические значения.
Принятие требует всех следующих наблюдений. Численные допуски сохранены из
первого опыта, до получения результатов родной координаты:

- До Ready получен ValuesChanged начального запроса с положительным requestId,
  event position и readback q = 0.5. Metadata, Ready и сценарий согласованы;
  другого движения до Ready нет.
- После Ready доставлен ровно один Touch PointerPressed в пределах 2 DIP от
  заданной точки; TryRedirectForManipulation вернулся для того же pointerId.
  Ошибка физического расстояния допускается до двух пикселей. Exit 0 CLI
  не заменяет доставку.
- Получены Interacting, минимум два разных ValuesChanged и Inertia с requestId 0.
  Программных запросов после нажатия нет.
- Последнее значение перед Inertia изменило q на ±0.25 с абсолютным допуском
  0.08 и правильным знаком. Запас 25.6 DIP учитывает распознавание жеста
  и объединение событий; это критерий опыта, а не обещание ОС.
- Скорость −nativeVy/H имеет правильный знак. Отношение к номинальной скорости
  ±0.25/0.3 s находится в [0.25, 2.5]. Полоса обнаруживает потерю, смену знака
  и крупную ошибку масштаба, не устанавливая точную калибровку скорости.
- Неактивные оси position/readback/velocity остаются в пределах одной native
  unit. Первая изменившаяся event position после Inertia продолжает направление
  последней event position до неё. Live readback может опережать callbacks,
  поэтому сравниваются последовательные event positions.
- Idle наступает не позднее пяти секунд после Inertia; position и readback
  находятся у цели с допуском q = 0.001. Для H = 320 это 0.32 native unit;
  прежняя квалификация диапазона 1000 не доказывает эту точность автоматически.
  Ошибки и обрезанная трасса запрещены, процесс закрывается штатно.

`node test/windows/assert-touch.mjs <evidence>` пишет `result.json`. PASS требует
обоих направлений. Отсутствие доставленного touch при готовом приложении —
INCOMPLETE; и FAIL, и INCOMPLETE дают ненулевой код. Подмены скорости, оси,
requestId, readback и доставки проверяют чувствительность oracle; runtime
доказывается событиями настоящего приложения.

## Сохранённые результаты предыдущих опытов

`41506273050`, source `49bc2c4`: все четыре запуска подтвердили позицию 500,
но проверка ждала повторного IdleStateEntered. [Таблица TryUpdatePosition](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.composition.interactions.interactiontracker.tryupdateposition?view=windows-app-sdk-2.0)
указывает: из Idle обновляется значение без смены состояния. Готовность
исправлена через ValuesChanged и readback; проверка Idle после Inertia сохранена.

`41510265053`, source `4116995`: touch доставлен во всех четырёх случаях.
Y→X и Y→Y modifiers с gain −1000/H дали правильный drag, но velocity осталась
в исходной Y без преобразования. X после отпускания не изменился и не достиг
цели. Y сообщил скорость против направления drag; в `y-up` наблюдён обратный
шаг около 0.4373 DIP. Эти результаты не объявляются PASS новой реализацией.

[Документация прямой привязки](https://learn.microsoft.com/en-us/windows/apps/develop/composition/interaction-tracker-manipulations)
показывает отрицательные bounds и −tracker.Position. [Delta modifiers](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.composition.interactions.visualinteractionsource.configuredeltapositionymodifiers?view=windows-app-sdk-2.0)
относятся к кадрам Interacting. Поэтому следующий опыт сохраняет родные
координаты вместо коррекции скорости через дополнительный UI-thread запрос.
Непрерывность этого способа ещё требует собственного runtime-результата.

PTP, mouse drag, горизонтальный ввод, смена DPI/размера, прерывание новым
намерением, точная калибровка, визуальная плавность и производительность
остаются за пределами этого протокола.
