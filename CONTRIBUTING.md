# Вклад в @labpics/motion

## Цель изменений

Каждое изменение должно улучшать наблюдаемое поведение потребителя и сохранять инварианты движка. GitHub Issues описывают задачи и их статус. Планы выполнения, handoff и отчёты рабочих сессий хранятся вне продуктового репозитория. Документация описывает действующие контракты.

Для CI действуют [общие правила публичной экосистемы Lab UI](https://github.com/Labpics-Team/labui/blob/main/CONTRIBUTING.md#проверить-изменение).

## Архитектурные границы

- Доменная математика не зависит от DOM, фреймворков и глобального времени.
- Платформенные возможности подключаются через адаптеры и инжектируемые швы.
- Публичный API принадлежит домену субпути; внутренние детали не экспортируются.
- Правила UI-компонентов принадлежат потребителю. Runtime принимает значения, цели,
  ввод и геометрию; примеры компонентов используют публичные импорты из `examples/`
  и рецептов. Компонентные фабрики и типы в пакет не добавляются.
- Один факт имеет один источник правды. Производные таблицы и манифесты генерируются или проверяются скриптами автоматической проверки.
- Новая возможность не должна увеличивать неиспользуемые субпути: `sideEffects`
  содержит только точный allowlist реально авто-регистрирующих входов.
- Автономное движение использует compositor-путь, когда семантика платформы это допускает. Интерактивная follow-фаза остаётся на main-потоке.

## Рабочий процесс

1. Создайте или выберите issue с пользовательским результатом, инвариантами, критериями приёмки и не-целями.
2. Зафиксируйте текущее поведение characterization-тестом, если меняется существующий контракт.
3. Добавьте RED-тест, который падает по требуемой причине.
4. Реализуйте минимальное изменение без параллельного второго источника правды.
5. Выполните рефакторинг только при зелёном наборе тестов.
6. Обновите документацию действующего контракта и `CHANGELOG.md`, если изменение заметно потребителю.
7. Откройте небольшой PR с одним связанным пользовательским результатом.

История RED-фазы хранится в PR и коммитах. В коде и тестах остаются только устойчивые пояснения: какой закон защищён и почему он важен.

## Метаданные Issues

Открытая рабочая задача имеет по одному label из каждого обязательного измерения:

- `type:*` — `bug`, `feature`, `hardening` или `docs`;
- `priority:*` — `P0`, `P1`, `P2` или `P3`;
- `status:*` — `ready`, `blocked` или `needs-adr`;
- `milestone:*` — версия, в которой должен появиться пользовательский результат.

`area:*` добавляется при одном явном домене-владельце. `epic` и `roadmap` используются только для агрегирующих задач и не заменяют дочерние спецификации.

Значения статуса:

- `status:ready` — все архитектурные развилки закрыты, зависимости доступны, задачу можно реализовывать по критериям приёмки;
- `status:blocked` — в body перечислены конкретные незавершённые зависимости;
- `status:needs-adr` — решение о границе владения или публичном контракте ещё не принято; реализация до ADR запрещена.

Приоритет задаёт риск, а не привлекательность функции:

- `P0` — безопасность, поставка или блокер текущей версии;
- `P1` — обязательный контракт активного milestone;
- `P2` — следующий слой после обязательных зависимостей;
- `P3` — неблокирующая объяснимость, инструменты или дальнейшая оптимизация.

Заголовок начинается с `[X.Y]` и совпадает с `milestone:X.Y`. Канонический порядок версий живёт только в roadmap issue.

## Стратегия тестирования

Выбирайте минимальный уровень, способный обнаружить дефект:

- чистая математика — unit- и property-тесты с известными оракулами;
- публичная поверхность — contract/pin-тесты;
- взаимодействие модулей — sociable integration-тесты без моков собственного кода;
- DOM, WAAPI, layout и browser lifecycle — тесты в реальном браузере;
- исправление дефекта — регрессионный тест на класс поведения, а не только на одну строку;
- критические численные домены — seeded fuzz и mutation testing.

Не подменяйте браузер самодельным объектом там, где проверяется поведение браузера. Не используйте wall-clock как функциональный оракул: время должно быть виртуальным или инжектируемым.

CI сохраняет полноту обычного Vitest-набора через настоящий discovery, а браузерный
набор выполняет все доли Chromium, Firefox и WebKit. Driver properties входят в этот
обычный Vitest-набор; отдельный повтор в PR не нужен. Mutation проверяет силу suite
в PR, на `merge_group`, каждом новом main и ручном запуске CI. Итоговый `CI` требует
успеха каждой обязательной проверки, включая driver mutation. Эти свойства и порядок
подготовки среды перед потребителем проверяет [контракт workflow](test/ci-workflow-contract.test.ts);
названия промежуточных шагов и число полных браузерных долей могут меняться.

Версию pnpm для обычных проверок задаёт `package.json#packageManager`;
`corepack install` использует это объявление без отдельного global pin.
Browser typecheck выполняется один раз через обязательный `check:static`.
Проверки пакета и браузера собирают `dist` из своего checkout. Driver mutation
работает с `src` и выбранными Vitest-тестами; предварительная сборка ему не нужна.

### Найти и запустить проверку

Файл называет компонент и поведение, `describe` — проверяемую границу, а имя теста —
условие и наблюдаемый результат. Например, `test/ci-workflow-contract.test.ts` →
`CI: итог обязательных проверок` → `не принимает пустой или повреждённый итог`.
Набор, задание CI и доля параллельного исполнения имеют
разное назначение: [suite](https://vitest.dev/api/describe) объединяет поведение, а [job](https://docs.github.com/en/actions/about-github-actions/understanding-github-actions#jobs) распределяет исполнение.

Проверки workflow запускают настоящие Bash-команды: для них нужен Bash **4.1
или новее**, где `[[ … ]]` подчиняется `set -e` ([изменение GNU Bash](https://groups.google.com/g/gnu.announce/c/xvx66bHeCxA)).
В Linux и macOS Bash выбирается через `PATH`. Системный Bash 3.2 в macOS не подходит;
установленный современный Bash должен стоять первым в `PATH`, например с Homebrew:

```sh
brew install bash
export PATH="$(brew --prefix bash)/bin:$PATH"
bash --version
```

В Windows [тест workflow](test/ci-workflow-contract.test.ts) использует
`%ProgramFiles%\Git\bin\bash.exe` из Git for Windows, а не `PATH`.
Если `ProgramFiles` не задана, используется `C:\Program Files\Git\bin\bash.exe`.
Проверяйте версию именно этого файла: Git в другом каталоге автоматически не обнаруживается.

Список выводится из самих тестов, без отдельного каталога. В Vitest 5 обычный
`list` разбирает файлы статически и не раскрывает варианты `it.each`.
[`--no-static-parse`](https://vitest.dev/guide/cli#vitest-list) импортирует файлы
для сбора полного списка, но не выполняет тела тестов:

```bash
pnpm exec vitest list test/ci-workflow-contract.test.ts --no-static-parse
pnpm exec vitest run test/ci-workflow-contract.test.ts
pnpm exec vitest list test/ci-workflow-contract.test.ts --no-static-parse -t 'требует успех mutation на push: failure'
pnpm exec vitest run test/ci-workflow-contract.test.ts -t 'требует успех mutation на push: failure'
pnpm exec playwright test --list --project=chromium
```

Reporter `default` в Vitest раскрывает дерево при запуске одного файла и при ошибке.
Для нескольких выбранных файлов или сокращённого вывода в среде агента можно явно
добавить `--reporter=tree`.
Адресный запуск проверяет только выбранное поведение, не весь обязательный CI.
Фильтр имени без совпадений может вернуть exit 0 с одними skipped-тестами:
проверяйте, что итог показывает непустой выполненный набор. `vitest list`
с `--no-static-parse` и теми же фильтрами помогает уточнить выбор, но не заменяет запуск.
Если выбранный тест читает собранный пакет, сначала выполните `pnpm build`;
`pnpm test` уже включает сборку. Браузерные тесты всегда требуют `dist`;
Playwright показывает файл, свойство и браузер в штатном `list`-выводе.

## Производительность

Оптимизация принимается только вместе с:

- воспроизводимым сценарием;
- baseline и измерением после изменения;
- функциональным тестом, не позволяющим ускорить код ценой контракта;
- размерным бюджетом для затронутой точки входа;
- явными ограничениями методологии.

Сравнение с другими библиотеками выполняется на одинаковом сценарии, одинаковом окружении и реальных опубликованных пакетах. Симуляция не публикуется как измерение.

## Комментарии и документация

Комментарии объясняют причину, ограничение или инвариант. Пересказ кода удаляется.

Документация пишется на русском языке и разделяется по назначению:

- обучение — первый рабочий путь;
- практические руководства — решение конкретной задачи;
- справочник — точный контракт API;
- объяснение — архитектура и принятые компромиссы.

В продукте сохраняются руководства, контракты, эталоны и материалы воспроизводимых проверок. Рабочие записи агентов отклоняются проверкой tracked-документов; локальные результаты бенчмарков остаются вне Git.

## Обязательные проверки

```bash
pnpm typecheck
pnpm build
pnpm audit                         # supply-chain advisories, порог moderate
pnpm test                          # включает проверку docs-drift
pnpm size
pnpm pack:smoke
pnpm pack:compat                   # ESM/CJS/TypeScript/Vite/SSR из реального тарбола
node scripts/check-docs-facts.mjs  # фактические доки (install, bench-отчёт)
node scripts/check-issue-forms.mjs # схема issue forms и taxonomy
```

Для изменений численного ядра дополнительно:

```bash
pnpm mutation
```

Каденцию и break-порог планового mutation-прогона держат
`.github/workflows/mutation.yml` и `stryker.config.mjs` — не документация.

## Требования к PR

В описании должны быть:

- пользовательский результат;
- изменённый контракт;
- доказательство RED → GREEN или characterization → изменение;
- риски и не-цели;
- результаты обязательных проверок;
- данные замеров для performance-изменений;
- запись в changelog для заметного потребителю изменения;
- независимое adversarial review для нового доменного механизма, release chain или platform adapter.

Автор PR и агент, создавший изменение, не считаются независимыми reviewers. Автоматический reviewer дополняет, но не заменяет профильный human review для security-critical и release-critical изменений.

Мерж запрещён при незакрытом P0/P1-дефекте в затронутом контракте, неразрешённом review thread, недостоверном performance-утверждении или отсутствии обязательного независимого review.

## Документация

Редактируйте Markdown в `docs/`. VitePress использует эти же файлы для сайта;
страницы из `package.json#files` входят в публичную документацию.
Оформление и навигация находятся в `docs/.vitepress/`.

```bash
pnpm docs:dev
pnpm docs:build
pnpm docs:preview
```

Для проверки навигации, поиска и мобильного чтения установите браузеры
командой `pnpm exec playwright install --with-deps chromium firefox webkit`,
затем выполните `pnpm docs:build && pnpm docs:test` на тестовом runner.
Для размещения в подпапке задайте `DOCS_BASE=/имя/` при сборке и preview.
Результат сборки находится в `docs/.vitepress/dist`.

Браузерные проверки библиотеки в `browser/` требуют только её `dist`.
Сборка сайта выполняется отдельно и не входит в npm-публикацию.
