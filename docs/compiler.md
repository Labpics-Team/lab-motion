# Компилятор: специализация при сборке

> **Diátaxis:** справочник.
>
> Контракт `./compiler/vite` и `./compiler/runtime`: статические анимации
> специализируются на этапе сборки. Область и цепочка реализованы в
> `src/compiler/core.ts`; расхождение документации с кодом — дефект.

Если вызов анимации статичен, его кривую можно вычислить при сборке. Плагин
заменяет такой вызов готовым артефактом: в браузерный граф потребителя не
попадают ни spring-солвер, ни парсер, только компактный исполнитель
`./compiler/runtime`, единственный браузерный артефакт компилятора.

```typescript
// vite.config.ts
import { motionCompiler } from '@labpics/motion/compiler/vite';

export default { plugins: [motionCompiler()] };
```

## Область первого среза

Поддерживается ровно один класс вызовов: статический
`animate(target, { opacity: N })` из прямого именованного импорта
`@labpics/motion/nano` без опций. Всё остальное приводит к консервативному
отказу от специализации: исходный код сохраняет прежнюю семантику и исполняется
обычным путём среды выполнения. Непредставимая программа или расхождение
проекции — **ошибка сборки, а не скрытый запасной путь**.

появляется.

## Как строится доверенный артефакт

Цепочка: nano SSOT (`springLinear`) → кандидат MotionProgram V1 →
`parseMotionProgramV1` (единственный оракул доверия) → проекция обратно в
`{ frame, durationMs, cssLinear }` с обязательным bit-exact сверением с
исходным nano-артефактом. Ядро компилятора не зависит от парсера: адаптер
передаёт ESTree-совместимый Program (для Vite/Rollup — штатный `this.parse`,
acorn) и сам применяет возвращённые байтовые правки.

Карта исходного кода имеет точный формат версии 3: сохранённые байты исходника
идут сегмент-в-сегмент, включая многострочные вызовы, чьи правки схлопывают
строки. Замена целиком отображается в начало своей правки, дописанный
hoisted-импорт исполнителя не отображается, поскольку это не пользовательский
код; `sources` содержит id модуля, поэтому композиция последующих карт не
теряет соответствия.

## Контракт диагностической трассировки

Инструменты репозитория могут вывести машинно-читаемые строки `tooling-trace`.
Каждая запись имеет `schemaVersion: 1`, `id`, `goal`, `owner`, `path`,
`execution` и обязательное поле `refusal`: `null` для `compiled`, непустая
причина отказа от специализации для `runtime`. Изменение состава или семантики
полей требует увеличения `schemaVersion`; неизвестную версию потребитель обязан
отклонять, а не угадывать.

Трассировка описывает фактически собранный граф и печатается только после
успешной приёмочной проверки компилятора; в публикуемый пакет и браузерную
среду выполнения она не входит.

Практический запуск описан в [рецептах](recipes.md#диагностика-compiler-lowering).

## Гарантии

- **Приёмочная проверка CI** (`pnpm acceptance:compiler`): реальная сборка Vite
  буквального примера выше с плагином и без него доказывает элиминацию солвера
  и парсера из бандла потребителя и строго меньший вес артефакта.
- **Сравнительная проверка в браузере**: тот же буквальный скомпилированный
  вызов сверяется с исходным в Chromium, Firefox и WebKit
  (`browser/*.spec.ts`).
- **Размерные потолки**: `./compiler/runtime` — точный ратчет, рост которого
  требует отдельного решения; `./compiler/vite` осознанно несёт parser+SSOT
  как цену доверенного артефакта на стороне сборки и никогда не поставляется
  браузеру. Актуальные числа проверяет `pnpm size`.
